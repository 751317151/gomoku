# 持续运营产品路线

更新日期：2026-11-24。当前以单实例、小规模上线验证为落点；每轮交付完整功能与对应回归，不以游戏数量替代稳定性和留存效果。

## 已具备的产品闭环

- 20 种玩法，双人及部分 2–8 人对局，匹配、人机、观战、重连与回放；包含 2–4 人飞行棋、9×7 斗兽棋、4×8 暗棋、2–8 人炸弹猫与 3 人斗地主（叫地主/底牌/完整牌型/倍数结算）。
- 游客升级账号，成长、成就、签到、每日任务、赛季与活动经验；密码找回、恢复码轮换与会话撤销已有本地端到端回归。
- 好友申请、实时私聊及离线留言、全队同房开局；本轮补齐双人约战。
- 举报、禁言与封禁，公告、活动配置与运营看板。
- Docker/Caddy 部署脚本、健康检查、备份/恢复与项目验证入口。

这些能力说明可以组织封闭试玩；本地通过不代表公网生产环境、容量或用户留存已经验收。

## 优先级一：小规模上线与数据可靠性

1. **生产运行基线**：本地容器基线已验收——真实 Java 11 镜像构建、非 root/只读根、Compose 健康、真实 WS 对局、重启持久化、含 WAL 的卷备份恢复、Caddy 本地 CA 下的 HTTPS/WSS 与公网 actuator 404，均由 `scripts/verify-production.ps1` / `verify-https.ps1` 复现。**仍待在真实服务器完成**：公网域名 ACME/DNS、不同网络真实用户的对局与重连、容量压测、多实例；上线时记录版本、步骤和回滚方式。
2. **历史资产独立于记录窗口**（本地已完成，待生产验收）：成长、成就、累计战绩、赛季与运营窗口已改读 `data/games/archive.sqlite` 全量摘要索引，大厅列表仍只缓存最近 5000 条；索引可从 `index.jsonl` 幂等重建，写入失败会健康降级并重试。已在隔离环境以 5005 条旧日志验证迁移、重启、索引重建与日志截断/替换边界。生产服务器仍需完成一次「含 WAL 的备份 → 恢复 → 重启」演练，确认备份脚本覆盖 `archive.sqlite-wal`。
3. **可恢复存储**：为账号、身份、关系、奖励和对局定义存储边界，逐步引入可迁移的数据库与事务。先保证单实例的备份、校验和恢复，再考虑多实例共享状态。
4. **账号与接口治理（本地已完成，待生产验收）**：密码已使用 PBKDF2 + HMAC-SHA256（310,000 次）+ 每账号随机盐，旧哈希在成功登录时透明升级；登录与密码找回均有按用户名的失败限流，恢复码错误不泄露账号是否存在。改密、找回密码与主动轮换恢复码都会撤销相应旧会话，恢复码仅以哈希落盘且明文只展示一次。REST/WebSocket 冒烟与真实浏览器冒烟已覆盖恢复、单次使用、旧码失效、全部设备退出和窄屏操作。生产仍需用真实试玩账号验证邮件/客服之外的恢复流程、弱网下的会话撤销时效、账号滥用监控与合规留存；本轮未实现邮箱/手机号找回。

## 优先级二：知道玩家为何回来或离开

1. **产品漏斗（本地已实现，待真实流量验证）**：服务端已在 `HALL_BIND`、`JOIN`、真实开局/终局/再开、重连边界记录六阶段事件，按入口与真人/人机拆分；看板展示阶段转化、各入口开局/完局率、等待分桶、匹配失败原因与重连成功率。身份只落加盐哈希，按日保留 90 天。下一步是用真实试玩流量确认口径与样本量，而不是继续堆指标。
2. 分开统计纯真人、人机与社交约战，跟踪等待时间、完局率、重连成功率及 D1/D7 留存；先建立基线，再为小步改动比较前后表现。漏斗已覆盖等待/完局/重连，D1/D7 仍由对局记录派生。
3. **玩法教程与结算出口（本地已完成并验证）**：20 种玩法已共用大厅/对局内规则面板，覆盖目标、步骤、提示、人数与计时，可从规则直接进入人机练习，桌面和 390px 手机均通过真实浏览器断言。结算浮层现可直接「返回大厅」，关闭浮层后底部仍同时保留「再来一局 / 返回大厅」，手机 390px 四按钮换行且无横向溢出，结算冒烟 23/23 通过。**多人重开等待反馈（本地已完成并验证）**：服务端权威维护准备名单与 60 秒确认窗口，电脑自动准备；准备/撤回双向实时广播，最后一人撤回立即取消，超时自动回到结算页且不会误开局；结算浮层与底部操作条同时展示进度和倒计时，手机 390px 按钮 ≥44px 且无溢出；真实双 WebSocket 22/22、双浏览器（桌面 + 手机）19/19 通过。**结算解释个性化与低人口连续开局（本地已完成并验证）**：全部玩法共用个性化结算解释与「下次可以」建议；结算原因由服务端 `finishReason` 区分正常终局、认输、超时、断线、提前离场与平局，避免误报；公开匹配房无电脑席位时，结算浮层与底部操作条提供「匹配下一局」，私人房/约战房/人机房保持原出口；公开匹配 20 秒无人加入时提示可补电脑，取消后继续等待。真实 Chrome 双上下文 21/21（桌面 1280px + 手机 390px，含 44px 触控、无横向溢出、旧房隔离与新公开房匹配），`RoomLifecycleTest` 11/11。**仍待继续打磨**：上述体验是否真正降低首局流失、提升重开率，需用真实试玩数据判断。
4. 用公告、经验活动和每日目标组织试玩，观察重复游玩与好友带来的回访；奖励规则要有明确边界，避免刷局影响竞技资产。

## 优先级三：内容扩展与扩容

- **玩法广度（本轮已完成）**：新增斗地主，3 人、54 张牌、叫 1–3 分地主并领取 3 张底牌；支持单张/对子/三带/顺子/连对/飞机/四带二/炸弹/火箭，炸弹与火箭翻倍，春天/反春天结算，两名农民共享胜负。手牌按视角裁剪，底牌在确定地主后才公开；出牌以手牌下标提交，服务端校验牌型，客户端不能伪造牌面。AI 只读取自己的手牌与公开桌面牌。接入人机、三人匹配、观战、回放、成就与规则教程。规则单测 7/7、引擎测试 8/8、房间测试 1/1。下一步仍应根据完局、回访与玩法尝试率选择游戏，避免只凭数量扩张。
- 根据真实完局和回访数据选择后续新增游戏；复用现有视角裁剪、回合边界、计时、存档和多人座位协议。
- 将超大前端脚本按网络/大厅/社交/对局拆分，在既有协议与 UI 冒烟保护下逐步迁移。
- 以压测结果决定 WebSocket 房间分片、共享在线状态与水平扩容；当前纯内存队伍、约战和房间不能直接当作多实例状态使用。

## 每轮交付约定

- 先识别并保留已有工作区改动，再选可验证的产品增量。
- Java 测试、脚本语法和缓存版本检查通过；涉及社交开局须运行多连接协议及真实双页面验证。
- 测试服务使用隔离目录和测试端口，浏览器使用独立身份；不污染真实资产。
- 记录实际完成、未验证范围与下一步；公网发布、迁移真实数据或扩大流量必须以具体环境的验证结果为依据。
